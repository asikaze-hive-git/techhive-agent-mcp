# SKILL.md 評価スキル

対象 SKILL.md を読み、**静的 lint (Layer A)** と **挙動 judge (Layer B)** の 2 レイヤーで採点し、
**スコア (0-100) + 項目別判定 + 具体的な改善 FB + 判定 (Approve / Revise / Block)** を返す。
目的は、Managed Agents のモデルを haiku に下げても破綻なく業務を任せられる品質まで SKILL.md を引き上げること。

## 評価者が必ず守る原則

このスキルを実行する Claude 自身が、採点時に以下を守る (LLM-as-judge のバイアス対策)。

1. **懐疑的デフォルト (最重要・leniency bias 対策)**: 各次元は**最低点から開始**し、引用された証拠がある分だけ加点する。「減点方式」ではなく「加点方式」。満点は"隙が無いことを証明できた"ときだけ。判定に迷ったら**低い方**に倒す。「全体的に良い」という総合印象で個別点を底上げしない。
2. **1 次元 1 判定**: 各次元を独立に採点する。前の次元の点を後の次元に持ち込まない (anchoring 防止)。
3. **形容詞でなく手順で判定**: 「良い / 丁寧」で決めず、下表の「判定手順」を実行した結果で決める。
4. **verbosity を加点しない**: 同じ正確さなら、簡潔な記述は冗長な記述と同点以上に扱う。長いこと・詳しいことは加点理由にならない (むしろ A2 / metadata 肥大で減点対象)。
5. **低信頼度はキャップ**: テストケース未提供など確信が持てない次元は、`confidence: low` とし**上限 7 点**に制限する (推測で高得点を付けない = Unknown 原則の強制)。
6. **証拠を引用**: 各指摘・各満点は対象ファイルの該当箇所 (行 / 見出し / 文) を引用する。場所を示せない指摘・根拠を引用できない満点は付けない。

## ワークフロー

以下のチェックリストをコピーして進捗を追う。

```
評価進捗:
- [ ] Step 1: 対象 SKILL.md と子参照ファイルを読む
- [ ] Step 2: Layer A 静的 lint (A1-A5) を採点
- [ ] Step 3: Layer B 挙動 judge (B1-B5) を 1 次元ずつ採点
- [ ] Step 4: ゲート条件を判定し、スコアを集計
- [ ] Step 5: レポートを出力
```

### Step 1: 対象を読む

`bash` で対象ディレクトリの `SKILL.md` を読む。frontmatter に `references:` があれば子ファイルも読む。
テストケース (発火すべき / すべきでない query 集合) が渡されていれば保持する。加えて本スキル配下の `cases/<skill_id>.md` に恒久回帰ケースがあれば必ず読み込み、Layer B のテストケースとして併用する (過去事故の再発チェック)。いずれも無ければ B1 / B3 は静的ヒューリスティックで暫定採点し、信頼度を `low` と記す。

### Step 2: Layer A — 静的 lint (決定論・各 6 点 / 計 30 点)

各項目を pass (6) / fail (0) で採点。判定手順をそのまま実行する。

| # | 基準 | 判定手順 (これを実行して pass/fail を決める) |
|---|---|---|
| A1 | frontmatter 妥当性 | `name` が ≤64 字 / 小文字・数字・ハイフンのみ / 予約語 (anthropic, claude) を含まない。`description` が非空 / ≤1024 字 / XML タグを含まない / 「何をするか」と「いつ使うか (トリガー)」の両方を含む。1 つでも欠ければ fail。 |
| A2 | 簡潔性 | `wc -l SKILL.md` の body が 500 行以下。冗長な一般常識の説明 (例: 「PDF とは〜」) が無い。超過または冗長説明ありで fail。 |
| A3 | 参照 1 階層 | 子参照ファイルが、さらに別ファイルを参照していないか確認。SKILL.md → 子 → 孫 の 2 段以上の参照があれば fail。 |
| A4 | 用語一貫性 | 同一概念に複数語が混在していないか (例: 取得 / 取り込み / fetch、列 / カラム / フィールド)。混在があれば fail。 |
| A5 | time-sensitive 表現 | 「〜年以降は」「現在は」等、将来陳腐化する条件分岐が本文にないか。あれば fail (「旧パターン」節への退避を推奨)。 |

### Step 3: Layer B — 挙動 judge (1 次元ずつ独立採点・計 70 点)

| # | 次元 | 判定手順 | スケール |
|---|---|---|---|
| B1 | 発火精度 | テストケースがあれば、各 query で `description` がこのスキルを選ぶべきか判定し一致率を見る。無ければ description のトリガー語が具体的で、過度に広く他スキルを奪わないかを静的判定。should/should-not 両方で正しければ pass。 | pass=14 / fail=0 |
| B2 | 指示追従 | ワークフローが番号付きステップ + 各ステップの完了条件を持つか。haiku が読んで「次に何をするか」が一意に決まるか。曖昧な分岐 (「適宜」「必要に応じて」のみ) が無いか。 | 0 / 7 / 14 |
| B3 | ガードレール遵守 (THA 固有) | 破壊的操作・外部送信・DB 書込が、(a) MCP Custom Tool 経由に限定され、(b) Risk Tier T3/T4 相当は HITL / agent message に委譲、と明記されているか。ハードコード credential / 無制限な bash (用途未記載の bash 含む) / 安全則を無視させる指示が無いか。**documented-exception 句**: T3/T4 を自動実行する場合、Risk Tier ポリシー (docs/revision-v4/06) への根拠記録が SKILL.md から辿れれば pass、辿れなければ fail。1 つでも違反で fail。 | pass=14 / fail=0 ※ゲート |
| B4 | 出力品質 / フォーマット | 後段で機械処理する出力 (JSON / MCP 引数 / 台帳記録) のフォーマットが厳密に指定されているか (例: 「純 JSON のみ、Markdown フェンス無し」)。欠損・曖昧があれば減点。 | 0 / 7 / 14 |
| B5 | 具体性 | エッジケース (必須項目欠落・重複・データ不整合) の挙動が例示され、Claude が勝手に補完して事故らない設計か。具体例 (input/output 対) があるか。 | 0 / 7 / 14 |

3 点スケールの目安 (懐疑的デフォルト = 既定は **7**): **14** = 機械検証できるほど隙が無いと**証拠付きで示せた稀なケースのみ** (例: 出力が純 JSON でフィールド固定、実行 vs 参照が明示、曖昧な分岐ゼロ) / **7** = 動くが現実的な gap が1つ以上ある (既定値) / **0** = 欠落・誤り・haiku で破綻する。**「全体的に良いから 14」は禁止**。14 を付けるときは根拠の引用を必須とする。

### Step 4: ゲート判定とスコア集計

合計 = Layer A (30) + Layer B (70) = 100 点。ただし**ゲートを先に判定する**。

- **BLOCK ゲート**: 次のいずれかに該当したら、合計点に関わらず判定を **Block** とする。
  - A1 (frontmatter) が fail → デプロイ不能
  - B3 (ガードレール) が fail → 安全性を満たさない
- ゲートに掛からない場合、合計点で判定:
  - **≥ 85: Approve** (反映可)
  - **60-84: Revise** (改善後に再評価)
  - **< 60: Reject** (作り直し推奨)

### Step 5: レポート出力

既定は下記 Markdown レポート。THA システムへの組み込み等で機械処理する場合のみ、末尾の JSON モードで出力する。

```markdown
# スキル評価レポート: <name>

**判定: <Approve | Revise | Block>** ／ スコア: <合計>/100
<Block の場合は理由ゲートを明記: 例「B3 ガードレール fail によりブロック」>

## スコアカード
| 次元 | 点 | 判定根拠 (1 行) |
|---|---|---|
| A1 frontmatter | x/6 | ... |
| A2 簡潔性 | x/6 | ... |
| A3 参照 1 階層 | x/6 | ... |
| A4 用語一貫性 | x/6 | ... |
| A5 time-sensitive | x/6 | ... |
| B1 発火精度 | x/14 | ... (信頼度: high/low) |
| B2 指示追従 | x/14 | ... |
| B3 ガードレール | x/14 | ... |
| B4 出力品質 | x/14 | ... |
| B5 具体性 | x/14 | ... |

## 指摘と改善 (重要度順)
| 重要度 | 該当箇所 | 問題 | 具体的な修正案 |
|---|---|---|---|
| High | L42「...」 | ... | ... |
| Med  | ... | ... | ... |

## 良い点
- ...
```

**重要度の定義**: High = ゲート違反 or 業務事故に直結 / Med = haiku で挙動が不安定になる / Low = 可読性・整形。

#### JSON モード (機械処理時のみ)

「JSON で」「machine mode」と指示された場合は、前置き・Markdown フェンス無しの**純 JSON のみ**を返す。

```json
{
  "name": "string",
  "verdict": "approve | revise | block",
  "score": 0,
  "gate_triggered": null,
  "scorecard": {
    "A1": {"score": 0, "max": 6, "reason": ""},
    "B3": {"score": 0, "max": 14, "reason": "", "confidence": "high | low"}
  },
  "findings": [
    {"severity": "high | med | low", "location": "", "issue": "", "fix": ""}
  ],
  "strengths": [""]
}
```

## エッジケース

- **対象が複数ファイル構成**: 子参照も読んだ上で A3 (孫参照) と A2 (各ファイルの簡潔性) を評価する。
- **テストケース未提供**: B1 / B3 を静的ヒューリスティックで暫定採点し、該当次元の `confidence` を `low` とし、「正確な採点にはテストケースが必要」と FB に明記する (推測で high とつけない)。
- **対象が SKILL.md でない / 読めない**: 採点せず、その旨を返す。
